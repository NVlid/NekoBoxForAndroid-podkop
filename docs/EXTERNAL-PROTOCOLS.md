# Встроенные DNScat2 и sshuttle (экспериментальная интеграция)

Оба адаптера регистрируются **внутри libcore/sing-box**:
`libcore/dnscat2` и `libcore/sshuttle`. Это не внешние Android-плагины,
не процессы Termux, не перенаправление на локальный SOCKS и не изменение
исходного podkop-ядра. Исходники транспорта и тесты находятся в `dnscat2/`.

Профили: «Добавить → Вручную → DNScat2 / sshuttle».
Импорт/экспорт поддерживается через универсальные `sn://`-ссылки NekoBox.
В экспорт попадают учётные данные: не публикуйте эти ссылки.
Конфигурация и ключи в обычном журнале приложения маскируются.

## Общие ограничения

- **Только TCP.** UDP, QUIC и ICMP не поддерживаются; UDP не подменяется
  прямым подключением. DNS приложения продолжает следовать настройкам NekoBox.
- Работают маршруты, выбор профиля для приложения и URL-test через обычный
  outbound-механизм. DNScat2 не проверяется TCP-ping: транспорт использует DNS/UDP.
- Глобальный режим «Напрямую» не меняется. Чтобы проверить весь трафик через
  выбранный туннель, выберите соответствующее действие в «Маршрутах».
- Версия схемы Room: 7; миграция 6→7 добавляет nullable `tunnelBean`.
  Не устанавливайте старую версию приложения поверх новой без резервной копии:
  прежний код проекта использует destructive fallback при downgrade базы.
- Автотесты не заменяют проверку на реальном Android и на вашей сети.

## DNScat2

Шифрование P-256 / SHA3-256 / Salsa20 и DNS-кодирование соответствуют
[спецификации upstream](https://github.com/iagox86/dnscat2/blob/master/doc/protocol.md).
PSK обязателен. Отсутствуют shell/exec, загрузка файлов и управление устройством.

**Для выхода в Интернет необходим companion из этого проекта.**
Обычный интерактивный Ruby-сервер dnscat2 не принимает клиентский
`TUNNEL_CONNECT` для произвольного удалённого назначения.
Наш companion принимает существующие CONNECT/DATA/CLOSE в обратном
направлении; для half-close добавлен `TUNNEL_EOF = 0x1003` (ID: uint32).
Tunnel ID равен request ID исходного CONNECT и не переиспользуется в сеансе.
Сторонний dnscat2-сервер не становится совместимым от одного названия профиля.

На VPS (Linux, Go 1.26):

```sh
cd dnscat2
go build -trimpath -o dnscat2-companion ./cmd/dnscat2-companion
umask 077
openssl rand -hex 32 > secret.txt
./dnscat2-companion -listen 0.0.0.0:5353 -secret-file secret.txt
```

Готовый Linux amd64 companion также собирается workflow Preview Build.
Разрешите выбранный **UDP**-порт в firewall. Не передавайте секрет в аргументах
процессов. Альтернатива secret-file — переменная `DNSCAT2_SECRET`.
Companion является аутентифицируемым прокси с доступом к сети VPS:
используйте свой сервер, сильный PSK, непривилегированного пользователя,
firewall и при необходимости ограничения исходящей сети. Не открывайте его
для посторонних и не используйте стандартные тестовые секреты.

В приложении для прямого режима:

- адрес сервера: IP вашего VPS;
- порт: 5353 (или фактический порт companion);
- домен: пустой;
- PSK: содержимое secret.txt без завершающего перевода строки;
- записи: `TXT` (также поддержаны `CNAME,MX,A,AAAA`);
- период опроса в простое: 1000 мс; допустимо 50–60000 мс.

Для рекурсивного DNS-режима нужна **NS-делегация отдельного домена** к VPS.
Companion должен быть доступен как авторитативный DNS на UDP/53:

```sh
./dnscat2-companion -listen 0.0.0.0:53 \
  -domain tunnel.example.net -secret-file secret.txt
```

Не запускайте весь сервис от root только ради порта 53: используйте
ограниченную capability или перенаправление порта средствами ОС.
В профиле укажите IP доступного DNS-резолвера/порт 53 и делегированный домен.
Большой домен уменьшает полезную нагрузку; слишком длинный домен отклоняется,
если в запрос уже не помещается 73-байтовый ENC INIT.
Политики DNS-резолверов и рекурсивное кеширование могут блокировать туннель.
Локальная скорость тестов не характеризует скорость реального DNS-туннеля.

У dnscat2 нестандартная криптографическая конструкция и 48-битный MAC:
это не TLS 1.3 и не профессионально аудированный VPN. Не считайте
экспериментальную интеграцию доказанно безопасной для чувствительных данных.

## sshuttle

Клиент реализует настоящий протокол `SS` из `sshuttle/ssnet.py`:
TCP_CONNECT/DATA/EOF/STOP, PING/PONG, synchronization `SSHUTTLE0001`.
SSH используется для **exec Python-сервера**, а не для `direct-tcpip`.

На сервере:

```sh
python3 -m venv ~/nekobox-sshuttle
~/nekobox-sshuttle/bin/pip install sshuttle==1.3.2
```

В профиле:

- адрес/порт SSH-сервера и имя пользователя;
- пароль **или** приватный ключ (и passphrase при необходимости);
- проверенный публичный **host key** сервера в формате `ssh-ed25519 AAAA…`
  либо другом поддерживаемом SSH-формате;
- Python: абсолютный путь `…/nekobox-sshuttle/bin/python` на VPS.
  Значение `python3` допустимо, если именно в этом окружении установлен sshuttle.

Получите host key через доверенный административный канал, например из
`/etc/ssh/ssh_host_ed25519_key.pub` на VPS. Не доверяйте слепо результату
неаутентифицированного `ssh-keyscan`.

Требуются SSH exec и установленный Python 3 с sshuttle 1.3.2. Автоматической
загрузки Python-кода на сервер нет. Другие версии отклоняются, поскольку
используется внутренний API upstream. Root/iptables, Python и SSH CLI на
Android не нужны. Автоматическое обнаружение сетей/hosts не включается:
правилами управляет NekoBox.

## Проверки

```sh
cd dnscat2
python3 -m pip install sshuttle==1.3.2
SSHUTTLE_TEST_PYTHON=python3 go test -race ./... -count=3
```

Включены официальные ECDH/key-derivation vectors, проверка подписи/nonce,
потерь handshake/rekey, SEQ wraparound, DNS codec для пяти типов записей,
настоящий UDP/DNS→TCP echo, reset и half-close, deadlines и ограничение буфера.
Тест sshuttle запускает установленный upstream Python-сервер, а не второй
Go-клиент. CI дополнительно собирает исходный C-клиент dnscat2 v0.07 и проверяет
его encrypted/authenticated handshake с companion. Тест C-клиента не доказывает
поддержку NekoBox-расширений стандартным Ruby-сервером.
